# Hims & Hers — Sr. Staff Frontend Engineer — Cheat Sheet
Org-level frontend architecture · customer-facing systems · NYSE: HIMS · remote-friendly

## What the role is
Org-wide frontend architecture leadership: set the architectural vision for customer-facing frontend, scale design systems + shared UI infra across teams, champion UI performance/a11y, establish patterns and governance, mentor senior engineers, navigate ambiguity. Sr Staff = senior-IC architect track (NOT people management).

## Your one-liner
"I build and scale the design systems, shared infrastructure, and developer tooling that let a whole org ship fast, consistent, high-quality UI — and I set the architecture and standards that keep it holding up as the org grows."

## Signature stories
1. **Redesign design system + governance.** 50+ component system (Storybook + Chromatic) across a 10–15 eng org, 30% dev-time cut, visual-regression governance, onboarding method (backend → prod React in a month), IC→Director staying hands-on. → design systems at scale + standards + mentorship.
2. **ForgeKit — DX as a product.** Open-source CLI + MCP suite, 5,700+ installs, standardizes design-to-code scaffolding and conventions. → developer experience, tooling, architecture.
3. **Emscripten browser CV (NARS).** Compiled OpenCV→JS via Emscripten for real-time in-browser CV. → deep UI-performance credibility.
4. **Monorepo architecture (Pineapple / PHC).** Nx monorepos + shared libraries across 8+ apps, 30+ shared libs. → shared frontend infrastructure across teams.

## Full-stack / Python framing (honest)
"Full-stack, frontend-deep — production Node.js, plus working Python/FastAPI. My production backend is Node/Nest; I've built with FastAPI at a working level and ramp fast." Never inflate Python.

## Their questions → your move
- "Scaled design systems across multiple teams?" → Redesign (org-wide) + Pineapple/PHC (shared libs across apps) + ForgeKit. Yes.
- "Drive architecture decisions / alignment across teams?" → SME + design reviews + patterns/standards; ForgeKit conventions; cross-functional liaison.
- "Org-wide at scale?" → BE HONEST: biggest org ~15 eng; the shape is right (multi-team adoption), the blast radius at a public company is a step up I'm ready for. Don't oversell.
- "Python / full-stack?" → the framing above.
- "UI performance approach?" → 40% render-overhead cut, concurrent rendering, Emscripten/WASM, Chromatic; measure with real user metrics.
- "Mentorship / raising the bar?" → onboarding methodology, design reviews, standards, IC→Director.
- "Ambiguity?" → five 0-to-1 startups, founded ForgeKit solo.

## Questions to ask them
- "What's the current state of the design system / shared frontend infra — greenfield, fragmented across teams, or maturing?"
- "Where's the biggest frontend-architecture pain as you scale — performance, consistency, velocity, or org boundaries?"
- "How do frontend teams share standards today, and what's worked or not?"
- "What does success for this role look like in the first 6–12 months?"

## Landmines / notes
- Sr Staff = IC-architect, not manager. Lead with technical leadership / patterns / mentorship, not headcount.
- Org scale — own the honest boundary; frame multi-team design-system adoption as your proof, own the step-up.
- Python — working / FastAPI level only.
- Customer-obsession — they emphasize it; tie architecture to customer/UX outcomes, not just technical elegance.
- Comp — public company, competitive + equity/ESPP; anchor on Staff scope/level.
